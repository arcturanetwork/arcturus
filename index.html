what arcturus is

A bound operator, not a language model with a chat interface.

Arcturus is the agent that carries out the network's work. It doesn't operate on trust in its own judgment. It operates inside published limits — reasoning frameworks, memory architectures, guardrails, and evaluation gates that are visible, checkable, and reproducible.

The difference between a chatbot and an agent is the same as the difference between a search box and an operating system. Arcturus is the latter. It plans multi-step workflows, calls external tools, retrieves grounded knowledge, manages episodic and semantic memory, and routes its own outputs through safety guardrails before anything reaches a user.

DOMAIN 01 15% · Agent Architecture

Reasoning Frameworks — ReAct, Reflexion, ReWOO

ReAct — The Foundational Agent Loop

ReAct (Reasoning + Acting) is the base pattern. The agent thinks, acts, observes, and repeats until the task is complete. Every thought produces an action; every action produces an observation; every observation feeds the next thought.

─── ReAct Loop ───────────────────────────────

  User Query
      │
      ▼
  ┌───────────┐
  │  THOUGHT   │  "I need to search for X"
  │  (reason)  │  LLM generates reasoning + plan
  └─────┬─────┘
        │
        ▼
  ┌───────────┐
  │  ACTION    │  search_documents({"query": "X"})
  │  (execute) │  LLM selects tool + writes args
  └─────┬─────┘
        │
        ▼
  ┌───────────┐
  │ OBSERVATION│  [{"doc": "policy-001", ...}]
  │  (observe) │  Tool returns structured result
  └─────┬─────┘
        │
        ▼
  ┌───────────┐
  │  THOUGHT   │  "Result confirms Y, now I need Z"
  │  (reason)  │  LLM incorporates observation
  └─────┬─────┘
        │
   ... repeat ...
        │
        ▼
  ┌───────────┐
  │  ANSWER    │  Final response to user
  │  (finish)  │  No tool call = task complete
  └───────────┘

Each step: Thought + Action in one LLM call.
Observation: Injected as system context
  for the next Thought (not a separate model call).
Token cost: Context grows linearly — each
  observation appended to the prompt window.
Failure mode: If observation doesn't shift
  reasoning, agent loops without progress.
vs ReWOO: ReAct interleaves plan + execute.
  ReWOO plans ALL calls first, then executes.

When to use: Interactive tasks, tool-heavy workflows, unknown step counts. The default agent pattern.

When not to use: Multi-step tasks where all tool calls are known upfront — use ReWOO instead.

Reflexion — Verbal Self-Reflection

After a failed attempt, the agent generates a verbal reflection — a natural-language critique of what went wrong — and stores it in episodic memory. The next attempt retrieves and reads that reflection before starting, creating self-improvement across iterations without weight updates.

─── Reflexion Cycle ──────────────────────────

  Attempt 1 → Result: FAIL
       │
       ▼
  ┌──────────────┐     ┌─────────────────┐
  │ Self-Reflect  │────▶│ Store in         │
  │ (what failed?)│     │ Episodic Memory  │
  └──────────────┘     └─────────────────┘
                                │
  Attempt 2 ←──── recall ───────┘
  (reads prior reflection, adjusts approach)

Key: No weight updates. Improvement via language memory.
Cost: Each attempt is a full generation cycle.

ReWOO — Plan All Calls Upfront

ReWOO (Reasoning WithOut Observation) decouples planning from execution. The agent plans all tool calls in a single pass, executes them, then synthesizes. This eliminates the ReAct loop's token overhead — up to 5× reduction in API calls.

─── ReWOO Pattern ────────────────────────────

  Step 1: PLAN
  #E1 = Search[query A]
  #E2 = Search[query B]
  #E3 = Lookup[#E1, term]

  Step 2: EXECUTE (all calls, no reasoning between)
  #E1 → result_1
  #E2 → result_2
  #E3 → result_3

  Step 3: SOLVE (synthesize all evidence)
  Answer = LLM[task, #E1, #E2, #E3]

Token efficiency: ~5× over ReAct.
Limitation: Can't adapt if early calls reveal
  the plan needs to change.

When to use: Research tasks, data aggregation, multi-source synthesis where the plan is predictable.

Plan-and-Solve

Decompose the task into subtasks before any tool calls. Each subtask is then executed independently. Useful for complex, multi-domain tasks where the structure is known but the execution path varies.

DOMAIN 02 15% · Agent Development

Agent Development & Tool Integration

Multi-Agent Coordination

Arcturus can operate as part of a multi-agent system. Three coordination topologies cover the majority of production patterns:

─── Multi-Agent Topologies ───────────────────

  Hierarchical          Sequential          Parallel

    [Orchestrator]      [Agent A]→[B]→[C]   [Agent A]
       /        \                             [Agent B] → [Synth]
   [Agent A] [Agent B]                     [Agent C]

  Best for:           Best for:            Best for:
  Complex tasks       Pipelines, each      Independent
  needing delegation  step transforms      research tasks
  • Hierarchical: An orchestrator delegates to specialized sub-agents. Best for complex tasks requiring different capabilities.
  • Sequential: Agents execute in chain — each transforms its input and passes to the next. Best for pipelines.
  • Parallel: Agents execute simultaneously on independent subtasks, then merge results. Best for research and synthesis.

Coordination failure modes to watch for:

  • Infinite loops (Agent A calls Agent B, B calls A — no termination condition)
  • Cascading hallucination (one agent invents something, the next builds on it)
  • Context contamination (agents share context window, polluting each other's reasoning)

Tool Calling Architecture

Tools are the agent's hands. Arcturus calls tools via structured function declarations — the LLM receives a schema, emits arguments, the orchestrator executes, and returns the result as an observation.

  • Function declarations: JSON schema with name, description, and typed parameters — the LLM selects and fills them
  • Side effects: Tools that modify state (write to DB, send email) require confirmation or guardrails
  • Error handling: Tool failures return structured errors the agent can reason about, not silent crashes
  • NVIDIA NeMo Agent Toolkit: Tools defined as YAML actions in NeMo Agent workflows

Agent-to-Agent (A2A) Protocol

Agents expose their capabilities via capability cards — machine-readable declarations of what an agent can do, what it needs, and what it returns. This enables dynamic discovery and composition of agent services.

DOMAIN 03 13% · Evaluation

Evaluation and Tuning

The RAG Triad

Three evaluatable properties of any retrieval-augmented generation:

PropertyQuestionMeasured From
Context RelevanceDid we retrieve the right chunks?Query → retrieved context
GroundednessIs the answer based on the context?Answer → context
Answer RelevanceDoes the answer address the query?Answer → query

If any one fails, the pipeline fails. RAG evaluation isn't about the LLM — it's about the junctions between components.

NAT Eval — The Three Levers

NVIDIA's NeMo Agent Toolkit provides three levers for agent evaluation:

  • Profiling: Trace agent execution — token counts, tool calls, latency per step, retry counts
  • Observability: OpenTelemetry integration — distributed tracing across agent → tool → model
  • Evaluation: Automated eval gates — run the agent against test cases, score outputs, gate deployments
─── NAT Eval Pipeline ────────────────────────

  dataset.jsonl
       │
       ▼
  ┌──────────────┐     ┌────────────┐     ┌───────────┐
  │ nat eval run  │────▶│ score outputs│────▶│ pass/fail  │
  │ (parallel)    │     │ (metrics)    │     │ gate CI/CD │
  └──────────────┘     └────────────┘     └───────────┘

  Metrics: accuracy, groundedness, tool-call accuracy,
  latency p50/p99, token efficiency, retry rate

Continuous Tuning

Evaluation feeds back into the system. Failed cases become test cases. Prompts are adjusted. Retrieval parameters are tuned. The agent improves through measured iteration, not vibes.

DOMAIN 04 13% · Deployment

Deployment and Scaling

Reference Architecture

Arcturus runs as a stateless orchestrator backed by NIM microservices. The orchestrator holds the reasoning loop; NIM holds the model inference. State lives in external stores — vector DB for memory, graph DB for relationships, document store for knowledge.

─── Production Architecture ──────────────────

  Client Request
       │
       ▼
  ┌─────────────┐     ┌──────────────┐
  │ API Gateway  │────▶│  Orchestrator │ (stateless)
  │ (auth, rate) │     │  (ReAct loop) │
  └─────────────┘     └──────┬───────┘
                             │
           ┌─────────────────┼─────────────────┐
           ▼                 ▼                 ▼
      ┌────────┐      ┌──────────┐      ┌──────────┐
      │  NIM   │      │ Tool Svc │      │ Mem Store│
      │(infer) │      │ (func)   │      │ (vector) │
      └────────┘      └──────────┘      └──────────┘
           │
           ▼
      ┌────────────┐
      │ Guardrails │ ← output screened before return
      │ (Colang)   │
      └────────────┘

Scaling NIM

  • Autoscaling: NIM pods scale on GPU utilization — H100/A100 targets, configurable min/max replicas
  • Connection pooling: Persistent connections between orchestrator and NIM reduce per-request latency
  • TensorRT-LLM optimization: Kernel fusion, KV-cache management, continuous batching — 2-4× throughput vs naive serving
  • Multi-model routing: Route requests by model capability — don't send a simple classification to an inference model

Stateless Orchestrator Pattern

The orchestrator is restartable. If it crashes, the conversation resumes from the last checkpoint. State is external — in Redis, in the vector store, in the graph database. This makes horizontal scaling trivial: add more orchestrator pods behind a load balancer.

DOMAIN 05 10% · Cognition

Cognition, Planning, and Memory

Memory Types

Arcturus doesn't have a single context window — it manages a memory stack:

TypeScopeExample
Short-term (Working)Current turnThe user's last message, current tool results
EpisodicPast interactionsWhat happened in last week's sessions
SemanticGeneral knowledgeDomain facts, concept relationships
ProceduralHow-to sequencesStep-by-step task recipes

Memory-Augmented Agent Loop

─── Memory Loop ──────────────────────────────

  User Input
       │
       ├──▶ Retrieve from Memory Store
       │    (semantic: facts, episodic: history)
       │
       ▼
  ┌──────────────┐
  │   Reason      │ ← context = input + retrieved memory
  │   (ReAct)     │
  └──────┬───────┘
         │
         ├──▶ Write result back to Memory
         │    (episodic: what happened)
         │
         ▼
      Output

Key: Memory is read AND written each cycle.
Risk: Episodic memory grows without
  compaction → retrieval quality degrades.

Planning Strategies

  • Single-path: Linear plan, execute, done. Simple tasks.
  • Tree-of-Thought: Branch reasoning into multiple paths, evaluate each, select best. Complex reasoning.
  • Decomposition: Break complex task into subtasks, delegate to sub-agents or sequential steps.

Context Window Management

The context window is finite. Arcturus manages it through: summarization of old turns, retrieval of only relevant episodic memory, and explicit eviction of stale context. The art is knowing what to forget.

DOMAIN 06 10% · Knowledge

Knowledge Integration — Graphs & RAG

Vector RAG vs Knowledge Graphs

Two different retrieval paradigms for two different question types:

MethodBest ForStrengthWeakness
Vector RAGLocal, factual lookupsFast, semantic matchingMisses multi-hop relationships
Knowledge GraphMulti-hop reasoningExplicit relationships, pathsRequires graph construction
GraphRAGGlobal, thematic questionsPre-computed community summariesBuild cost, indexing time

GraphRAG — How It Works

GraphRAG (Microsoft Research, 2024) pre-computes community summaries at index time. When a user asks a global question ("What are the main themes in this corpus?"), GraphRAG retrieves community-level summaries instead of individual chunks — solving the problem that vector RAG can't answer questions that span the entire dataset.

─── GraphRAG Pipeline ────────────────────────

  INDEX TIME (expensive, one-time):
  Documents → Entities → Relations → Graph
       │
       ▼
  Community Detection (Leiden algorithm)
       │
       ▼
  Summarize each community → store

  ────────────────────────────────────────

  QUERY TIME (fast, per-request):
  Global question → retrieve community summaries
       │
       ▼
  Map: each community answers the question
       │
       ▼
  Reduce: synthesize all community answers
       │
       ▼
  Final answer

Trade-off: Heavy index cost → fast + thorough
  global queries. Don't use for simple lookup.

NVIDIA's Knowledge Stack

  • cuGraph: GPU-accelerated graph processing — community detection, traversal, PageRank at scale
  • G-Retriever: Retrieves subgraphs relevant to a query — "zero-shot" question answering over graphs
  • AI-Q Blueprint: NVIDIA's reference architecture for building query-aware knowledge systems

The RAG Triad (Revisited)

Grounding is not a feature. A grounded answer is one that can be traced back to a specific source. If you can't trace it, it's not grounded — it's generated.

DOMAIN 07 7% · NVIDIA Platform

NVIDIA Platform — NeMo · NIM · Guardrails

NeMo Agent Toolkit (NAT)

The orchestration framework. NAT is framework-agnostic — it instruments the agent loop with profiling, observability (OpenTelemetry), and evaluation gates. Workflows are defined in YAML; tools are declared as actions with typed schemas.

─── NAT Workflow (YAML) ──────────────────────

  workflow:
    name: customer-support-agent
    steps:
      - name: classify_intent
        tool: nim.classify
        input: $user_message
        output: $intent

      - name: retrieve_context
        tool: rag.search
        input: $intent
        output: $context

      - name: generate_response
        tool: nim.generate
        input: [$intent, $context]
        guardrail: check_safety

      - name: log_interaction
        tool: telemetry.emit
        input: [$user_message, $response]

NIM Microservices

  • What: Containerized inference servers optimized with TensorRT-LLM for NVIDIA GPUs
  • Why: 2-4× throughput vs naive serving through kernel fusion, KV-cache management, continuous batching
  • Models: Llama, Mistral, Phi, Qwen, and more — each as a swappable NIM container
  • API: OpenAI-compatible — drop-in replacement for model calls, no code changes needed

NeMo Guardrails

Programmable input/output safety using Colang 2.0. Guardrails run between the user and the LLM — and between the LLM and the output. They can block, rewrite, or redirect based on rules defined in natural language.

  • Input rails: Classify and filter user input before it reaches the LLM
  • Dialog rails: Control conversation flow — canonical forms, topic constraints
  • Output rails: Screen LLM output before it reaches the user — toxicity, PII, hallucination checks
  • Colang 2.0: Structured natural-language programming for rail definitions

DOMAIN 09 5% · Safety

Safety, Ethics, and Governance

The Five Checks

Inherited from Arctura Network's Work Standard. Every proposed action is evaluated against five criteria — not by consensus, but by published rules:

  1. 01
    NeedIs there a real reason for this action?
  2. 02
    ClarityCan someone outside the room understand what happened and who owns it?
  3. 03
    UsefulnessDoes this serve the network, not just whoever proposed it?
  4. 04
    DurabilityWill this still make sense later?
  5. 05
    ReversalCan it be undone if the assumption is wrong?

Guardrail Layers

Three layers of defense between input and output:

─── Guardrail Stack ──────────────────────────

  User Input
       │
       ▼
  ┌──────────────┐  block: jailbreaks, injection
  │  Input Rails │  filter: profanity, PII detection
  └──────┬───────┘
         ▼
  ┌──────────────┐  route: topic constraints
  │ Dialog Rails │  enforce: canonical forms
  └──────┬───────┘
         ▼
     [ LLM Generate ]
         │
         ▼
  ┌──────────────┐  check: toxicity, hallucination
  │ Output Rails │  block: sensitive data leakage
  └──────────────┘

Bias and Fairness

Evaluation isn't just about accuracy. NAT eval can score for demographic bias in responses, refusal rates across user demographics, and disparate impact in tool-calling patterns. Bias is a production failure, not a research topic.

DOMAIN 10 5% · Interaction

Human-AI Interaction and Oversight

Handoff Protocol

Arcturus knows when it doesn't know. Any result outside its mapped authority, any disputed evaluation, any exception to the five checks — escalates to a person. The handoff is explicit, logged, and includes full context.

─── Handoff Flow ─────────────────────────────

  Agent executes → result is uncertain
       │
       ▼
  ┌──────────────┐     ┌──────────────────┐
  │ Confidence    │────▶│ Generate handoff  │
  │ check         │     │ package            │
  │ (threshold)   │     │ • context           │
  └──────────────┘     │ • reasoning trace   │
                       │ • what's uncertain  │
                       └───────┬───────────┘
                               │
                               ▼
                       ┌──────────────┐
                       │ Human reviewer │
                       │ resolves       │
                       └──────────────┘

Transparency by Default

  • Reasoning trace: Every output links to the reasoning steps and tool calls that produced it
  • Source attribution: Every factual claim in a grounded answer links to a retrievable source
  • Confidence signaling: Uncertain outputs are marked, not presented as confident
  • Human reviewable: The full execution trace is available for audit after any action

The Accountability Card

Borrowed from Arctura Network: every agent publishes a card declaring its owner, its role, its boundaries, and its handoff rules. Arcturus is held to the same standard it asks of any agent that joins the network.

An agent without a published accountability card is a black box. Arctura Network doesn't run black boxes.
